## S-0 조사 결과
- 세이브 = 한 개의 jsonb (`hd3d_progress.data`, localStorage `hd3d_save` 가 기준). 저장은 낙관적 동시성(updated_at) → 충돌 시 `P.merge(로컬, 서버)`.
- 장비 병합(`E.mergeEquip`): 아이템 id 기준 합집합 · 장착은 기기 우선 · 상자는 id 합집합, 가방에 같은 장비가 있으면 상자 정리.
- 서버는 아이템을 읽지 않음 (`hd3d_progress_summary` = 재화·별·영웅만) → **스키마 변경 불필요**.
- **서버 크기 제한** `check (pg_column_size(data) < 65536)` 은 *압축 전* jsonb 크기로 검사됨 (embedded PG 로 측정):
  장비 1개 ≈ 290바이트(jsonb). 가방 최대 60(CAP 40 + 정리 여유 20) + 상자 200 = 약 78.8KB → 이미 한도 초과(기존 잠재 문제, 이번 범위 밖 · 보고). 창고 100칸을 같은 모양으로 넣으면 한도를 쉽게 넘음
  → 서버로 보낼 때만 창고 장비를 짧은 문자열로 압축(`ST.packSave`) — 1개 ≈ 90바이트.
- 가방을 도는 곳: 분해·강화·재설정·각성·제작(가방 가득)·장착·상자 개봉(가방 빈칸) → **가방만** (창고 장비는 꺼내서 사용).
  고유 보유(`ownsUnique`)·uqLog 자가 치유·도감 등록·상자/우편 고유 중복 판정·병합의 고유 강화/각성 큰 값·도감/스테이지 고유 카드 표시 → **창고 포함**.

## 설계 (S-1~S-3 결과)
- 위치: 마을 — 오른쪽 레일 **📦 창고** 버튼(`#twStor`, 개수 `#twStorN`) 또는 가방 패널(I 키·🎒) 의 탭 `[🎒 가방][📦 창고][📖 도감]`. 창고 탭이면 패널이 `.wide`.
- 화면: 왼쪽 가방(장착 중 제외) · 가운데 창고 · 오른쪽 선택 카드. 클릭 = 선택 → ▶ 보관 / ◀ 꺼내기 버튼, **Shift+클릭 / 더블클릭 = 바로 옮기기**,
  `일괄 보관 ▶` / `◀ 일괄 꺼내기` = 지금 필터(부위·등급·◆고유)에 맞는 것 전부 (정렬 순서대로 빈칸만큼). 정렬: 등급·전투력·강화·종류·최근.
- 용량: 60칸 → 단계마다 +10, 4단계(최대 100칸). 비용(단계별, **강철 또는 영혼석 중 하나**): 120/500 · 200/900 · 320/1500 · 480/2400. 확인창 있음.
  고유도 1칸 차지. 꺼낼 때 가방(CAP 40) 가득이면 일반 장비는 못 꺼냄(고유는 상자 개봉처럼 가능).
- 저장: `save.stor` (가방과 같은 모양) · `save.storX` 0..4 (0이면 키 없음). 옛 세이브 = 빈 창고. 서버로 보낼 때만 `stor` 를 짧은 JSON 문자열로 압축(`SG.packSave`, 장비당 ≈ 70~100바이트).
- 병합(복제·분실 없음): 가방+창고 id 합집합 → 한 장비는 한 곳 (병합된 장착에 쓰이면 가방 > 이 기기 위치 > 서버 위치), 고유는 강화·각성 큰 값, storX 큰 값.
  가방과 창고에 같은 id 가 있으면 가방 쪽만. 창고가 병합으로 칸을 넘으면 잃지 않고 넣기만 막음 (상한 300 = 망가진 세이브 방어). 가방 CAP+20 초과분은 버리지 않고 창고로.
- 옛 클라이언트(캐시된 JS)가 저장해 서버 행에서 `stor` 가 사라지면: 계정별 로컬 백업 `hd3d_stor_<uid>` 로 복구 후 다시 저장.
- 스키마 변경 없음 (서버는 아이템을 읽지 않음).
